# 报错阅读指南（ASan 篇）

> 整理自两次实战：10 章链表的 heap-use-after-free、11 章双链表的 SEGV。
> 编译命令：`clang -g -fsanitize=address -o app main.c dlist.c`（`-g` 必须加，否则没有行号）

---

## 0. 先分清：报错来自哪一层

程序出问题，抓你的"警察"有三层，越往下越晚、越暴力：

| 层次 | 谁抓的 | 什么时候抓 | 例子 |
|---|---|---|---|
| 编译期 | 编译器 | 还没生成程序 | 语法错误、类型不匹配、warning |
| 运行期·软件层 | ASan（编译时插桩） | 程序跑起来后 | heap-use-after-free、heap-buffer-overflow |
| 运行期·硬件层 | CPU 的 MMU + 操作系统 | 程序跑起来后 | **SEGV**（段错误） |

关键区分：
- **ASan 抓的**：地址技术上还能访问，但逻辑上非法（比如 free 过了）。没开 ASan 时程序可能**不崩、悄悄读到脏数据**——这才可怕。
- **SEGV**：地址根本不可访问，硬件直接拦截，**没有 ASan 也照崩**。ASan 只是帮你把现场（调用栈、寄存器）记录得漂亮一点。

---

## 1. ASan 报告的通用读法（三步）

不管哪种报错，报告都按同一个套路读：

### 第一步：看第一行——是什么罪名

```
==49870==ERROR: AddressSanitizer: SEGV on unknown address 0x000000000010
==12345==ERROR: AddressSanitizer: heap-use-after-free on address 0x603000000040
```

`AddressSanitizer:` 后面那个词就是罪名。见下面第 2、3 节分述。

### 第二步：看调用栈——案发现场在哪

```
    #0 0x0001026d4f44 in print_list dlist.c:83   ← 案发第一现场
    #1 0x0001026d5710 in main main.c:51          ← 谁叫它去的
```

- `#0` 是**出事的那一行**，`#1` 是调用它的地方，往下依次是调用链。
- 读法：`main.c:51` 调了 `print_list`，死在 `dlist.c:83`。
- 排查顺序：先看 #0 那行代码在解引用哪个指针，再顺着 #1、#2 往回追"这个指针是谁传进来的"。

### 第三步：看地址——指针的"尸检报告"

地址本身藏着大量信息，见第 4 节速查表。

## 2. 罪名一：heap-use-after-free（10 章实战）

**意思**：这块堆内存已经 `free` 了，你又回来读/写它。

**报告特征**：ASan 会给你**三段历史**，非常贴心：

```
READ of size 4 at 0x603000000040        ← 案发：谁在读
freed by thread T0 here:                ← 这块内存是在哪 free 的
    #0 ... in remove_node dlist.c:76
previously allocated by thread T0 here: ← 当初是在哪 malloc 的
    #0 ... in make_node dlist.c:24
```

**排查思路**：三段对着看——"malloc 在 A 处 → free 在 B 处 → C 处还在用"。九成是这两种：
1. free 掉节点后，还拿着指向它的旧指针在用（**悬垂指针**）；
2. 遍历删除时先 `free(p)` 再 `p = p->next`（顺序反了，要先存 next）。

**预防**：free 之后立刻把指针置 NULL。这不能防住所有情况（别的指针可能还指着那块内存），但能把这类 bug 转化成更好查的 NULL 解引用——见下一节。

---

## 3. 罪名二：SEGV / 零页（11 章双链表实战）

**意思**：访问了没有权限的地址，硬件当场拦截。SEGV = Segmentation Violation，即段错误（Segmentation Fault），信号名 `SIGSEGV`。

**类比**：操作系统给每个进程发了张地图，标明哪些内存是你家的。SEGV 就是拿着地址去敲不属于你的门，门卫（MMU）当场把你按住。

**报告特征**：

```
SEGV on unknown address 0x000000000010    ← 关键线索：小地址！
Hint: address points to the zero page.    ← ASan 直接递话了
    #0 in print_list dlist.c:83
```

### 零页是什么

虚拟地址空间从 0 开始的第一页（Mac 上 16KB），操作系统**故意**封死、永不分配。因为 `NULL == 0`，封死零页就能让所有 NULL 解引用**在案发第一现场立刻崩**，而不是读到垃圾继续带病狂奔。

```
0x0000 ┌──────────────┐
       │   零 页       │ ← 禁区。NULL(0x0) 和
0x0010 │  (封死)       │    NULL->next(0x10) 都落在这
       ├──────────────┤
       │   代码段      │
       │   堆(malloc)  │ ← 0x6030... 这种才是你家
       │   栈          │ ← 0x16d7...
       └──────────────┘
```

> 崩溃不是 bug 的代价，崩溃是保护机制送你的礼物。（早年无保护的系统里，NULL 解引用不崩，bug 能藏到天荒地老。）

### 为什么崩溃地址是 0x10？——反推结构体成员

```
DNode 内存布局（64 位）：
偏移 0x00: int data     (4字节 + 4字节对齐填充)
偏移 0x08: DNode *prev
偏移 0x10: DNode *next   ← 0x10 = 16
```

`head->next` = "从 head 出发走 0x10 字节去读"。head 为 NULL 时，读的就是 `0 + 0x10 = 0x10`。
**所以崩溃地址 = NULL + 成员偏移，能直接反推出你解引用的是哪个成员**：
- 崩在 `0x10` → 读的是 `->next`
- 崩在 `0x8` → 读的是 `->prev`
- 崩在 `0x0` → 读的是 `->data`（第一个成员）

### 一字之差的核心区分

- 读指针**本身**没事：`if (head == NULL)` 随便判（head 变量好好待在栈上）。
- 出事的是**解引用**：`head->next` 是去 head **指向的地方**读。

## 4. 地址速查表

看到崩溃地址，先对号入座：

| 地址长相 | 大概率是什么 |
|---|---|
| `0x0` 或很小（< 一页） | NULL 解引用，偏移量 = 结构体成员偏移 |
| `0x6030...`、`0x6240...` 开头 | ASan 管理的**堆**地址（malloc 来的）|
| `0x16d7...`、`0x7ff...` 开头 | **栈**地址（局部变量）|
| `0xbebebebe...`、`0xbe` 重复 | ASan 填充的"malloc 后未初始化"魔数 |
| `0x55555555...`、`0x55` 重复 | ASan 填充的"已 free"魔数 |

## 5. 附：打印顺序"错乱"不是 bug

调试时如果发现 stderr 的报错出现在 stdout 输出的**前面**（明明代码里是后触发的）：
- `stderr` **不带缓冲**，一写立刻落地；
- `stdout` 连终端时是行缓冲，被**管道/重定向接走时变全缓冲**，攒一大坨最后才刷。

所以输出顺序错乱 ≠ 执行顺序错乱。要强制刷可以 `fflush(stdout)`。

## 6. 排查流程 checklist

1. 看罪名：use-after-free（逻辑非法）还是 SEGV（地址非法）？
2. 看 `#0`：那一行在解引用哪个指针？
3. 看地址：小地址 → 找 NULL；堆地址 + use-after-free → 找 free 的历史。
4. 顺着调用栈往回追：这个指针是谁、在哪一步变坏的？
5. 修完重新编译（带 ASan）跑一遍，**跑之前先预测输出**。
